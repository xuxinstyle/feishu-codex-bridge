# 飞书任务引导方案与实现

## 目标

对齐 Codex 客户端「引导」按钮：运行中提交补充文字要求，继续当前任务；普通消息仍按 session 排队。

## 方案比较

| 方案 | 操作方式 | 优点 | 代价 |
| --- | --- | --- | --- |
| 自动引导 | 运行中的所有新消息自动追加 | 操作最少 | 无法区分补充要求和下一项独立任务，会改变已有队列习惯 |
| 仅命令 | `/steer <要求>` | 意图明确、实现简单 | 已经排队的消息需要额外操作 |
| 按钮加命令（采用） | 排队文字消息显示「引导」；也支持 `/steer` | 与客户端交互一致，保留正常排队 | 需要处理按钮身份、重复提交和队列竞态 |

## 行为与接口

- 普通文字消息排队；存在同聊天、同项目、同 session 的运行中任务时，额外回复一张「引导」卡片。
- 点击「引导」或发送 `/steer task-xxxx`，将原排队消息提交给创建卡片时绑定的任务。
- `/steer <补充要求>` 和 `/引导 <补充要求>` 直接向当前 session 的运行中任务提交，不创建排队任务。
- 引导继承当前任务的模型和推理设置；本期只支持文字，不改动停止任务能力。
- 卡片按消息 ID、聊天和发送者校验，不受 `/panel` 的最新面板校验影响。
- `/new` 通过递增的会话代次使旧引导失效，同毫秒重置也能准确区分。

## 执行通道

独立 App Server 使用 [官方 `turn/steer`](https://learn.chatgpt.com/docs/app-server#steer-an-active-turn)，传递 `threadId`、`expectedTurnId` 和文字输入，不调用 `turn/interrupt` 或重新启动任务。

桌面通道沿用客户端自身的追加消息入口，在投递前核对正在观察的轮次，并省略模型及推理覆盖。已检查本机客户端的 `sendFollowUpMessage` 调度路径；桥接不另开 App Server 接管正在写入的会话。桌面追加入口不暴露 `expectedTurnId`，检查与投递间的自然结束仍由客户端处理；不能声称它具有独立通道同等的轮次原子校验能力。

## 队列与失败处理

引导独立于任务队列执行，同目标任务的引导按顺序提交。引导开始时同步锁住排队消息，任务队列等待投递结果后再决定是否启动：

| 结果 | 排队消息状态 | 后续处理 |
| --- | --- | --- |
| 确认收到 | `steered` | 不再作为独立任务执行，原任务回传最终结果 |
| 明确拒绝、未就绪或原任务已结束 | `pending` | 保持正常队列行为 |
| 投递后回执丢失 | `steer_unknown` | 暂停此消息的自动执行，提示到客户端核对，避免重复执行 |

重复点击复用同一投递；提交成功后的重复点击只返回原结果。提交期间不允许取消这条排队消息。引导失败不取消运行中的任务。普通排队消息和未知投递状态不新增持久化恢复承诺。

## 验证与交付

1. 命令解析、多行文字、文字与图片边界。
2. 运行中追加、无中断、原任务最终输出及控制资源释放。
3. 队列等待投递结果，成功不重复执行、明确拒绝继续排队、回执未知不自动重发。
4. 聊天、用户、卡片、session 和会话重置代次隔离。
5. 从实际消息处理器、卡片处理器到 TaskRunner 的本地集成测试，模拟飞书与 Codex 传输，不向真实聊天发送测试消息。
6. 全量 `npm test`、`npm run check`、`git diff --check` 通过后，以中文提交并普通推送至 `origin/main`；验证远程提交一致。
